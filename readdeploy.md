# Звіт про розгортання платформи PawBack (Deployment Report)

Цей документ описує архітектуру та процес розгортання платформи **PawBack** у хмарному середовищі. Платформа використовує мікросервісний підхід із розділенням на Frontend, Backend, Базу даних та Хмарне сховище для медіафайлів.

## 1. Архітектура розгортання

Усі основні компоненти системи розгорнуті на платформі **Render** (хмарний PaaS-провайдер), що забезпечує безперервну інтеграцію (CI/CD) та автоматичний деплой при оновленні коду в репозиторії на GitHub.

### 1.1. База Даних (PostgreSQL)
- **Платформа:** Render (Managed PostgreSQL)
- **Регіон:** Frankfurt (Європа) - вибрано для мінімізації затримок (ping) між сервером та базою.
- **Особливості:** База даних розгорнута з підтримкою розширень `postgis` (для роботи з геолокаціями та картами) та `pgvector` (для збереження векторних ембедингів AI-пошуку). Міграції виконуються автоматично за допомогою **Flyway** при запуску бекенду.

### 1.2. Backend (Spring Boot)
- **Платформа:** Render (Web Service)
- **Регіон:** Frankfurt (Європа)
- **Опис:** Java/Spring Boot додаток розгорнуто як веб-сервіс за допомогою Docker-контейнера. Він зв'язаний із базою даних через внутрішню захищену мережу Render, що забезпечує швидкість і унеможливлює доступ до бази даних ззовні. 
- **Зв'язок:** Бекенд приймає запити від фронтенду та забезпечує роботу REST API і WebSocket (для роботи чату в реальному часі).

### 1.3. Frontend (React + Vite)
- **Платформа:** Render (Static Site)
- **Опис:** Клієнтська частина платформи, написана на React та зібрана за допомогою Vite. Render автоматично запускає команду `npm run build` і роздає згенеровані статичні файли (папка `dist`) через свою глобальну CDN-мережу.
- **Зв'язок:** Фронтенд робить запити до бекенду, використовуючи змінну середовища `VITE_API_URL`, яка вказує на адресу розгорнутого бекенду (наприклад, `https://pawback.onrender.com`). Також налаштовано Rewrite-правило (`/* -> /index.html`) для коректної роботи React Router (запобігає помилці 404 при оновленні сторінок).

### 1.4. Хмарне сховище медіафайлів (Cloudinary)
- **Платформа:** Cloudinary
- **Опис:** Початково локальна розробка велася з використанням MinIO. Для продакшн-середовища (деплою) архітектуру було оптимізовано: замість розгортання власного S3-сервера використано спеціалізований хмарний сервіс **Cloudinary**.
- **Переваги:** Це забезпечує надійне та довічне збереження завантажених користувачами фотографій тварин, високу швидкість їх віддачі та суттєво зменшує навантаження і споживання пам'яті на сервері бекенду.

## 2. Процес розгортання (CI/CD)

Розгортання платформи було повністю автоматизовано. Процес виглядає наступним чином:

1. **Push у репозиторій:** Розробник заливає оновлений код у гілку `main` на GitHub.
2. **Автоматичний тригер:** Платформа Render відстежує зміни та автоматично фіксує нові коміти.
3. **Збірка (Build):**
   - *Бекенд:* Render запускає збірку Java-додатка за допомогою Gradle (`./gradlew build -x test`), після чого пакує його в Docker-образ згідно з інструкціями в `Dockerfile`.
   - *Фронтенд:* Render завантажує залежності (`npm install`) та збирає оптимізовані статичні файли для браузера (`npm run build`).
4. **Запуск (Deploy):** Нові версії сервісів підміняють старі без простою системи (Zero-Downtime Deployment). При старті бекенд автоматично застосовує міграції бази даних через Flyway та підключається до Cloudinary за допомогою захищеного API-ключа.

## 3. Змінні середовища (Environment Variables)

Для забезпечення безпеки, жодні паролі чи ключі доступу не зберігаються у відкритому вигляді в коді (в репозиторії). Замість цього використовуються захищені змінні середовища (Environment Variables) на рівні серверів Render:
- `SPRING_DATASOURCE_URL` — внутрішня (internal) адреса PostgreSQL бази даних.
- `DB_USER`, `DB_PASSWORD` — облікові дані для підключення до бази.
- `CLOUDINARY_URL` — секретний API-ключ для доступу до хмарного сховища фотографій.
- `VITE_API_URL` — змінна для фронтенду, яка вказує йому адресу розгорнутого бекенд-сервісу.
